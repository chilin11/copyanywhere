# 05 · 前端配合、实施顺序、上线与未决事项

## 1. 前端任务

前端文件都在 `public/`，可以新增模块文件（部署会整目录复制）。约束：不改 `public/crypto.js` 的算法与导出；不放宽 CSP（无内联脚本/样式、无外部资源）；规范见 [02](02-sync-contract.md)，界面见 [03](03-ui-design.md)。

| 任务 | 内容 | 主要文件 | 依赖后端 | 对应缺陷 |
|---|---|---|---|---|
| **F1 配对与空间身份** | ① `init()` 加错误边界；非安全上下文/无 WebCrypto 时整页提示（03 §3.1）。② 首屏「加入已有空间」：粘贴完整链接或 43 位密钥。③ 链接解析：不合法给出提示；与本机密钥不同时先校验目标空间再确认切换（03 §2.7）。④ 「空间不存在」整页流程，密钥移到 `ca.secret.prev` 而不是删除（03 §2.6）。⑤ 空间指纹显示在顶栏与添加设备对话框（02 §2）。⑥ iPhone Safari 的主屏幕提示（03 §2.3-4）。 | `app.js` `index.html` `style.css` | 无（见下方过渡规则） | C1 C2 C3 C4 C10 |
| **F2 同步引擎 v2** | 新模块 `sync.js` 实现 02 §6 的状态机 R1–R13；四态状态胶囊；在线设备数；版本横幅；元数据解密失败计数与占位卡。 | 新增 `sync.js`；`app.js` | B2 B3（回环自测需 B6） | C5 C6 C11 |
| **F3 发件箱** | 新模块 `outbox.js` 实现 02 §7：客户端 `itemId`、重试退避、失败常驻、取回文字、`sessionStorage` 镜像、分块续传；发送确认条使用 `peers`。 | 新增 `outbox.js`；`app.js` | B1 B4 B5 | C7 |
| **F4 布局改版** | 手机底部固定输入区、桌面双栏、空间条、筛选提示条、「↑ N 条新内容」、「⋯」菜单、16 px 输入字号、44 px 触控目标（03 §3–§5）。 | `index.html` `style.css` `app.js` | 无 | C9 C13 |
| **F5 自查与诊断面板** | 「对方看不到？」三步自查（03 §2.5）；连接诊断面板与复制诊断信息（02 §10.2）。 | `app.js` `index.html` | B6 | C4 C12 |
| **F6 分享入口** | SW 按分享批次分别缓存（不再整体清空 `ca-share`）；页面在记录 `committed` 后才删缓存；结果提示按真实结果；处理 `/?share=lost`。 | `sw.js` `app.js` | B8；与 F3 一起 | C8 |

**F1 的过渡规则**（B1 上线前服务器没有 `code`）：判断「空间不存在」时，若响应是 JSON 且有 `code` 字段，以 `code === 'space_not_found'` 为准；若没有 `code` 字段（旧服务端），以 `error === 'space not found'` 为准。除此之外的 404 一律视为暂时性故障。这是 02 §4.7「不得匹配 error 文本」的唯一例外，B1 上线并确认线上版本后删除。

**前端没有自动化测试设施**（仓库现有测试只覆盖服务端与 `crypto.js`）。本方案不要求新增测试框架；验收用第 3 节的手工用例。`sync.js` 的规则部分（R3–R7）建议写成不依赖 DOM 的纯函数，使其可以用现有的 `node --test` 直接测试——是否这样做由前端负责人决定。

## 2. 实施顺序

```
阶段 0  现场诊断（01 篇 §4，不改代码）            ─ 立即，决定后续优先级
阶段 1  F1                                         ─ 前端独立可发；直接针对可信度最高的假设 H1
阶段 2  B0 → B1 → B2 → B3     ‖  F4（并行，无后端依赖）
        然后 F2
阶段 3  B4 → B5 → B8          然后 F3 + F6
阶段 4  B6 → B7               然后 F5
```

- 每个后端任务独立可上线：全部为增量，旧前端不受影响（02 §11 混跑矩阵）。
- `proto: 2` 在 B3 的最后一步才对外；F2 以它为开关，未检测到则走 R13 降级。因此 **F2 可以先于 B3 合并，但不会先于 B3 生效**。
- F3 以 `/api/config.proto >= 2` 且首次带 `X-Item-Id` 的请求返回体含 `rev` 或 `duplicate` 作为幂等可用的依据；不满足时发件箱对单请求**不自动重试**（避免重复条目），只提供手动重试。
- 阶段 0 的结果如果否定了 H1 而指向 H3（实时通道），把阶段 2 提到阶段 1 之前。

## 3. 手工验收用例（集成阶段使用）

环境：一台电脑浏览器 + 一部手机，经真实域名（HTTPS，经过实际使用的隧道/反代）访问。每条记录「通过/失败/未测」。

| # | 步骤 | 期望 |
|---|---|---|
| M1 | 电脑创建空间；手机扫码加入 | 两端顶栏空间代号相同；在线数都为 2 |
| M2 | 手机打开一个被截断的配对链接 | 停在首屏并提示链接不完整；手机原有空间（如有）不受影响 |
| M3 | 手机已在空间 A，打开空间 B 的链接 | 出现切换确认，默认保持 A |
| M4 | 手机已在空间 A，打开一个不存在空间的合法格式链接 | 提示「链接指向的空间不存在」；仍在 A，密钥未丢 |
| M5 | iPhone：Safari 加入后「添加到主屏幕」，打开主屏幕 App | 首屏是「加入已有空间」；粘贴链接后进入同一代号的空间 |
| M6 | 手机发文字，电脑页面在前台 | 1 秒内出现；手机显示「已保存 · 另有 1 台设备在线」 |
| M7 | 电脑关闭页面，手机发文字 | 手机显示「当前没有其他设备在线」；电脑重新打开后内容在列表中 |
| M8 | 电脑端用开发者工具把 `/events` 请求阻断（或在反代上开启缓冲） | ≤ 8 秒状态变「轮询同步」；手机发送后 ≤ 5 秒出现 |
| M9 | 电脑休眠 2 分钟后唤醒 | ≤ 60 秒内状态恢复「实时同步」，休眠期间的内容全部出现，无需手动刷新 |
| M10 | 手机开飞行模式后发文字，再关闭飞行模式 | 发件箱显示等待重试；恢复后自动发出；电脑端只出现 1 条 |
| M11 | 手机上传 30 MB 文件，中途切到后台 10 秒再回来 | 回来后继续（续传），最终电脑端可下载且内容正确 |
| M12 | 发送一个超过上限的文件 | 发件箱红色常驻「超过大小上限」；可丢弃 |
| M13 | 电脑端筛选停在「文字」，手机发图片 | 出现「有 1 条新的图片〔查看〕」 |
| M14 | 服务重启（`systemctl restart copyanywhere`） | 两端数秒内自动恢复，列表不变，无重复无缺失 |
| M15 | 旧版页面（升级前已打开、未刷新的标签页）在升级后继续使用 | 仍能收发（v1 流）；刷新后进入新版 |
| M16 | Android：从相册「分享 → CopyAnywhere」连续两次 | 两批内容都发出；任何失败都留在发件箱 |
| M17 | 「对方看不到？」面板 | 三步各自显示本机实时判定；复制的诊断信息里没有密钥、没有完整空间 ID |
| M18 | 在 `http://<局域网 IP>` 打开 | 整页提示需要 HTTPS，不白屏 |

## 4. 上线与回滚
- 上线方式不变：重新运行安装命令（原子替换程序目录并重启）。数据无迁移。
- 每个阶段上线后观察：服务日志中的 `item_added.streams`（B7 之后）、用户反馈、诊断面板。
- 回滚：安装上一个版本即可；数据格式未变。新前端遇到旧服务端按 R13 降级。
- README 需要同步更新的内容（文档负责人处理，不在后端任务范围）：加入方式增加「粘贴配对链接」；iPhone 主屏幕 App 的说明；「服务器不记录访问日志」处补充事件日志与 `LOG_LEVEL=silent`；排障一节指向诊断面板。

## 6. 未验证事项（如实列出）

本方案产出过程中**没有**做以下任何一项：
- 没有启动服务，没有运行 `npm test`（任务要求不启动服务；B0 的第一步就是由实施者跑基线）。
- 没有在任何真机/浏览器上复现「手机发送后网页看不到」；01 篇 H1–H7 全部是假设。
- 没有验证 iOS 主屏幕 Web App 与 Safari 的存储隔离、iOS 输入框聚焦缩放在当前系统版本上的实际表现（均为平台已知行为，需 M5、真机确认）。
- 没有验证用户实际使用的隧道/反代是否缓冲 SSE（01 篇 D2）。
- 04 篇中的代码片段是示意，未经执行；测试用例未经编写与运行。
- 03 篇的布局没有原型，也没有做过可用性测试。
- 没有评估 500 条目 + 多设备下 `peers`/`ping` 帧的实际开销（按设计每连接每 25 秒约 100 字节，预期可忽略，未测量）。

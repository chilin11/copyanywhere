# 01 · 现状调查、证据与根因假设

> 基线：提交 `a9d6495`。所有 `文件:行号` 均指该提交。
> 调查方式：**只做了静态代码阅读**，没有启动服务、没有真机、没有复现用户现场。
> 因此本文把结论严格分成两类：
>
> - **C（Code-confirmed）**：代码路径确实存在，读代码即可证实的缺陷。"证实"指缺陷存在，不代表它就是用户现场的原因。
> - **H（Hypothesis）**：对「手机发送后网页看不到」的解释，**全部待复现**，第 4 节给出零代码的验证办法。

## 1. 现有架构与数据流

单进程 Node.js（`server.js`，无依赖）+ 原生网页（`public/`）。服务端只存密文。

```
secret(32B, base64url 43 字符；只在 URL #片段 与 localStorage「ca.secret」)
  ├─ HKDF(salt "copyanywhere-v1", info "copyanywhere/id")  → spaceId（服务器路由键）   crypto.js:25-34
  └─ HKDF(同 salt,           info "copyanywhere/enc") → AES-256-GCM 密钥（不出浏览器）
```

| 环节 | 客户端 | 服务端 |
|---|---|---|
| 创建空间 | `formCreate` 提交：生成 secret → `POST /api/spaces`（带服务器密码）`app.js:824-842` | `server.js:272-285`，内存 `spaces` Map + `spaces/<id>/index.json` |
| 配对 | `openAdd()` 生成 `origin/#s=<secret>` 二维码/链接 `app.js:812-817`；对端 `init()` 从 hash 取出写入 localStorage 并立刻抹掉 hash `app.js:954-959` | 不参与（服务器不知道有几台设备） |
| 打开空间 | `openSpace()`：`GET /api/spaces/:id` 取全量 → `syncItems()` → `connect()` `app.js:257-275` | `server.js:292` |
| 发送 | `upload()`：1 块走 `POST /items`（头 `X-Meta`），多块走 `/uploads` 分块 `app.js:666-730` | `server.js:330-353`、`374-439`；落盘后 `addItem()` 广播 `add` `server.js:160-169` |
| 实时 | `EventSource(/events)`；`onopen` 时 `resync()` 拉全量 `app.js:283-319` | SSE：首帧 `usage`，之后 `add`/`delete`/`usage`/`gone`，每 25 秒一个**注释行** `: ping` `server.js:304-317` |
| 列表对齐 | `syncItems(list)`：本地有而列表没有的一律删除，再逐条补 `app.js:321-326` | `GET /items` 返回当前数组 `server.js:324` |
| 页面回前台 | `visibilitychange`：SSE 已 CLOSED 才重连，否则只 `resync()` `app.js:931-937` | — |

关键事实：**实时性完全依赖浏览器对 SSE 连接健康度的判断**；全量对齐只发生在「SSE 打开时」和「页面回到前台时」两个时刻；快照与事件之间**没有任何版本号**。

## 2. 代码可证实的缺陷（C）

### C1 配对链接会静默替换、甚至清除本机密钥
- `app.js:954-956`：只要 hash 里匹配到 43 字符就 `localStorage.setItem(LS.secret, …)`，不比较旧值、不确认。
- 随后 `openSpace()` 对该空间 `GET` 得到 404 时直接 `localStorage.removeItem(LS.secret)`（`app.js:264-266`）。
- 后果：打开任意一个 `https://你的域名/#s=<43 个随机字符>`，本机原有空间的密钥被覆盖然后删除，页面落到「创建空间」。这既是可用性问题也是安全问题（一条链接即可让设备掉出空间）。
- 链接不合法（被聊天软件截断、尾部多了字符）时 `m` 为 null，hash 仍被抹掉（`app.js:955`），**没有任何提示**，页面要么静默打开旧空间、要么落到创建页。

### C2 任何 404 都被当成「空间已删除」并忘记密钥
- `app.js:264-266`、`277-281`（`spaceGone`）、`304`、`317`、`725`。判断依据只有 HTTP 状态码 404。
- 反向代理/隧道在上游切换、升级重启、配置错误时返回的 404，也会让设备删掉唯一的密钥副本。
- 服务器数据目录丢失（Docker 卷重建、`DATA_DIR` 配错、`--purge` 重装）后，每台设备都会各自落到创建页。

### C3 首屏只有「创建」，没有「加入」
- `index.html:36-41` 只有密码框 +「创建我的空间」；`index.html:47` 只有一句文字提示去别的设备扫码。
- 在「本浏览器没有密钥」的任何情况下（见 H1 的触发途径），用户在这台设备上能点的唯一按钮就是**新建一个空间**。

### C4 用户无法判断两台设备是否在同一个空间
- 顶栏只有连接状态（`index.html:22`、`app.js:226-230`），没有空间标识；服务端没有「在线设备」概念（`server.js:52` 的 `clients` 只是响应对象集合，不对外暴露数量）。
- 两台设备各在一个空间时，双方都显示「已连接」，完全正常，互相永远看不到对方内容。

### C5 快照与事件竞态：刚到的条目可能被旧快照删掉
- `resync()` 发出 `GET /items`（`app.js:313`）后，若服务端在生成该响应**之后**新增了条目 X，X 的 `add` 事件可能先于这份旧响应被处理（两条独立连接，无顺序保证）：`addEntry(X)` 入表 → 旧列表到达 → `syncItems` 第一行就把不在旧列表中的 X `dropEntry` 掉（`app.js:323`）。
- 之后没有任何机制把 X 补回来，直到下一次重连或页面切前台。
- 触发窗口是「一次 resync 的往返时间」，条件是恰好此时有新条目，**概率低、偶发**；列表越大/网络越慢窗口越宽。发送方自己的条目（`app.js:716-719`）同理。

### C6 SSE「假在线」：没有看门狗，也没有轮询兜底
- 心跳是 SSE **注释行**（`server.js:314`），`EventSource` 不会把注释交给 JS，客户端无法知道心跳是否到达。
- 客户端只在 `onerror` 时处理异常（`app.js:299-307`）。半开连接、被中间代理缓冲的流都不会触发 `onerror`，状态一直是「已连接」。
- 页面保持在前台时没有任何定时对齐（`app.js:931-937` 只在可见性变化时触发）。
- 结论：只要流「开着但不出数据」，电脑端会**无限期**看不到新内容且显示正常。

### C7 发送不可靠且失败不醒目
- 单请求上传（所有文字、≤8 MB 文件）**没有重试**：`app.js:685-688`；重试循环只存在于分块分支 `app.js:695-708`。
- 失败只弹 4 秒 toast（`app.js:726`），随后进度卡被移除（`app.js:728`）；输入框在发送前就已清空（`app.js:767`），文字无法找回。
- toast 是单例（`app.js:117-123`），后一条会覆盖前一条。
- 服务端条目 id 由服务器生成（`server.js:338`），请求成功但响应丢失时客户端无法安全重发（会重复）。

### C8 「分享到 CopyAnywhere」会丢内容并误报成功
- Service Worker 未接管页面时，`POST /share` 落到服务器，服务器**丢弃请求体**并 303 回首页（`server.js:449`），没有任何提示。
- Service Worker 每次收到分享都先整体清空缓存（`sw.js:24`），上一批还没被页面取走就会被覆盖。
- `consumeShareTarget()` 在上传**之前**就删除了分享缓存（`app.js:785`），上传失败即永久丢失。
- `upload()` 吞掉所有异常（`app.js:720-729`），所以 `Promise.all(jobs)` 永远成功，随后无条件提示「分享内容已发送」（`app.js:786-789`），并覆盖掉可能存在的「发送失败」toast。

### C9 筛选会隐藏新到的内容
- 选中「文字/图片/文件」后，其他类型用 CSS 直接隐藏（`style.css:283-285`、`app.js:856-861`）。电脑端停在「文字」时，手机发来的图片不可见，只有筛选条上的数字变化。

### C10 初始化没有错误边界
- `init()` 末尾直接 `await openSpace()`（`app.js:958-959`），整体无 `catch`（`app.js:962`）。两个主视图默认都是 `hidden`（`index.html:30`、`index.html:51`）。
- `crypto.subtle` 在非安全上下文（`http://局域网IP`）不存在，`deriveSpace` 抛错（`crypto.js:26`）→ 只剩顶栏的**白屏**，无提示。

### C11 元数据解密失败被静默丢弃
- `addEntry` 中 `catch { return; }`（`app.js:333`）。条目直接不显示，无计数、无日志。同一空间必然同钥，正常不会发生；但一旦发生完全不可见。

### C12 服务端零可观测性
- 全文件只有启动行与异常输出（`server.js:86`、`475`、`488`、`502`）。`/healthz` 只回 `ok`（`server.js:481`）。
- 无法回答最基本的排障问题：手机那次上传到没到服务器？落在哪个空间？当时该空间有几条实时连接？

### C13 移动端可用性问题
- 输入框 `font-size: 15.5px`（`style.css:202`）：iOS Safari 对小于 16px 的输入框聚焦时会放大页面（平台已知行为，**待真机确认**）。
- ≤560px 时工具按钮文字被隐藏，只剩图标（`style.css:493`）；输入区在页面顶部且不固定（`style.css:194-198`），列表一滚动就看不到。
- 发送结果、对端是否在线都没有持续可见的位置。

## 3. 对「手机发送后网页看不到」的假设（H，全部待复现）

可信度是基于代码路径的**主观排序**，不是测量结果。

| 编号 | 假设 | 依赖的缺陷 | 可信度 | 验证 |
|---|---|---|---|---|
| **H1** | 手机和电脑其实不在同一个空间 | C1 C2 C3 C4 | 高 | D1 |
| **H2** | 手机端那次发送实际失败或被丢弃，用户没注意到 | C7 C8 | 中高 | D3 |
| **H3** | 电脑端实时通道假在线或被反代缓冲 | C6 | 中 | D2 |
| H4 | 条目到达后被旧快照删掉 | C5 | 低（偶发） | 第 02 篇的 rev 测试 |
| H5 | 电脑端处于其他筛选，内容被隐藏 | C9 | 低–中 | D4 |
| H6 | HTTP/1.1 下同源标签页过多，SSE 占满 6 条连接 | — | 低 | D2 时看协议与标签页数 |
| H7 | 元数据解密失败被静默丢弃 | C11 | 很低 | 新版诊断面板计数 |

### H1 的具体触发途径（均有对应代码路径；平台行为需真机确认）
1. **iPhone「添加到主屏幕」**：README 第 5 步要求这么做。密钥只在 localStorage（`app.js:8`），hash 加载后即被抹掉（`app.js:955`），`manifest.webmanifest:5` 的 `start_url` 是 `/`。iOS 主屏幕 Web App 与 Safari 不共享 localStorage → 主屏幕 App 首次打开无密钥 → 创建页（C3）→ 用户输入密码**新建了第二个空间**。
2. **扫码用的浏览器 ≠ 日常用的浏览器**：微信/系统相机/其他 App 内置浏览器扫码后密钥存在那个 WebView 里，之后用 Chrome/Safari 打开域名没有密钥。
3. **链接片段丢失或被改写**：经聊天软件、「安全跳转」中间页转发时 `#…` 被去掉或追加字符 → 正则不匹配 → 静默落到创建页（C1）。
4. **服务器数据丢失后各自重建**（C2）：每台设备各自 404 → 各自创建。
5. **不同来源**：`http` vs `https`、域名 vs IP、带不带 `www`，localStorage 各自独立。

## 4. 现场诊断手册（阶段 0，不改代码）

把结果填进下表再决定优先级。任何一步都**不要**把完整空间 ID 或配对链接贴到聊天/工单里（空间 ID 等同于该空间密文的访问凭据）。

**D1 是否同一空间**（先做，最便宜）
```sh
# 原生安装
sudo ls -1 /var/lib/copyanywhere/spaces | cut -c1-6
# Docker
docker exec copyanywhere ls -1 /data/spaces | cut -c1-6
```
- 出现 ≥2 个目录 → 手机发送一条后看哪个目录的 `index.json` 修改时间变了（`stat -c '%y' <dir>/index.json`）；再在电脑浏览器 DevTools → Network 里看 `/api/spaces/<id>/events` 的前 6 位。两者不同 ⇒ **H1 成立**。
- 只有 1 个目录 ⇒ H1 不成立，继续 D2/D3。

**D2 实时通道是否通畅**（电脑上执行，`<id>` 取自电脑浏览器 Network 面板）
```sh
curl -N -s -D - "https://<域名>/api/spaces/<id>/events"
```
- 期望：立即看到响应头与一帧 `data: {"type":"usage"…}`；每 25 秒一行 `: ping`；手机发送后 1 秒内出现 `data: {"type":"add"…}`。
- 帧成批延迟到达、或只有头没有体 ⇒ 反代在缓冲 ⇒ **H3 成立**。同时记录响应是 HTTP/1.1 还是 HTTP/2（H6）。

**D3 手机是否真的发成功**
- 手机发送后在服务器看对应空间 `index.json` 是否新增条目（条目数：`grep -o '"id"' index.json | wc -l`）。没有新增 ⇒ **H2 成立**，再区分是网页内发送还是系统分享菜单（C8）。

**D4 展示层**
- 电脑端筛选是否停在「全部」；发送后手动切一次标签页（触发 `resync`）内容是否出现。切一下才出现 ⇒ 指向 H3/H4；筛选导致 ⇒ H5。

| 观察 | 结论 | 对应修复 |
|---|---|---|
| 两端空间前缀不同 | H1 | 前端 F1（可独立先发） |
| 服务器没收到 | H2 | 后端 B4/B5/B8 + 前端 F3、F6 |
| 服务器收到、curl 流里没有/延迟 | H3（代理） | 后端 B3、B6 + 前端 F2；并修正反代配置 |
| 服务器收到、curl 流正常、网页不显示、切标签页后出现 | H3（假在线）或 H4 | 后端 B2、B3 + 前端 F2 |
| 只在某筛选下不显示 | H5 | 前端 F4 |

## 5. 调查中确认「没有问题」的部分（避免误修）
- 加密方案本身（HKDF 派生、每块独立 IV、AAD 绑定角色与块序）与分块上传的服务端校验逻辑，未发现与本问题相关的缺陷；重设计**不改动** `public/crypto.js` 的任何算法与参数。
- 静态资源 `Cache-Control: no-cache` + ETag（`server.js:459-461`），Service Worker 不缓存页面（`sw.js:8-13`），不存在「旧 JS 被缓存」导致的问题；但**已打开的标签页**会继续运行旧 JS，新服务端必须兼容旧客户端（见 02 篇 §7）。
- 服务端对单进程内的条目顺序、容量预留、TTL 清理逻辑未发现与本问题相关的缺陷。
